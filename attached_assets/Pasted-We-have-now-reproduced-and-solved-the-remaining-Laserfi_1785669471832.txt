1. WHAT WE PROVED ON THE REAL MACHINE
============================================================

Laserfiche Repository API:

    https://localhost/LFRepositoryAPI

worked from PowerShell and the certificate actually presented by IIS was:

    Subject: CN=localhost
    Issuer: CN=localhost
    SAN: DNS Name=localhost
    Thumbprint on THIS MACHINE:
    972F61FC2D278A86BAA04CF87ECC6FA1DD1CD4A5

Certificate validity:

    NotBefore: 2025-09-02
    NotAfter: 2030-09-02

IIS HTTPS binding:

    *:443:

The certificate was located in:

    Cert:\LocalMachine\My

and the certificate chain itself was valid when inspected manually.

The Dashboard IIS application pool runs as:

    NetworkService

The Dashboard correctly constructed the Laserfiche token endpoint:

    https://localhost/LFRepositoryAPI/v1/Repositories/<runtime-repository>/Token

Therefore:
- repository propagation was correct
- API URL construction was correct
- /LFRepositoryAPI was not duplicated
- hostname matched the certificate
- Laserfiche API was reachable

But ASP.NET/.NET HttpClient failed with:

    AuthenticationException
    UntrustedRoot

The Dashboard therefore displayed:

    A secure (TLS) connection to the Laserfiche server could not be established.

The permanent manual fix that PROVED the root cause was:

1. Read the existing IIS certificate from LocalMachine\My.
2. Export ONLY the public certificate.
3. Import that public certificate into:

       Cert:\LocalMachine\Root

4. Keep the original certificate in LocalMachine\My.
5. Restart the Dashboard IIS application pool.

After that:

    LocalMachine\My\<thumbprint>   = True
    LocalMachine\Root\<thumbprint> = True

and Dashboard authentication immediately worked.

The Dashboard is now fully working from BOTH:

- Laserfiche Desktop Client
- Laserfiche Web Client

This proves the remaining failure was LocalMachine TLS trust.

5. SELF-SIGNED CERTIFICATE HANDLING
============================================================

The real Laserfiche installation used a self-signed certificate:

    Subject == Issuer
    CN=localhost
    SAN=localhost

The certificate existed in:

    LocalMachine\My

but was NOT trusted by the Dashboard NetworkService process until its public certificate was placed in:

    LocalMachine\Root

Implement this generically.

If ALL of the following are true:

1. The certificate is the certificate actually bound to the Laserfiche API HTTPS endpoint.
2. The certificate is currently valid by date.
3. The requested hostname matches SAN/CN.
4. The certificate is self-signed.
5. Chain failure is specifically UntrustedRoot/self-signed trust.
6. Installer is elevated.

Then the installer may install ONLY the PUBLIC certificate into:

    LocalMachine\Root

Do not export/import the private key into Root.

The original certificate/private key remains in:

    LocalMachine\My

Use X509Certificate2 / X509Store if possible instead of shelling out to PowerShell.

Conceptually:

    using (var root = new X509Store(StoreName.Root, StoreLocation.LocalMachine))
    {
        root.Open(OpenFlags.ReadWrite);

        if (!root.Certificates
                 .Find(X509FindType.FindByThumbprint, cert.Thumbprint, false)
                 .Any())
        {
            // Add public-only certificate.
            var publicCert = new X509Certificate2(cert.Export(X509ContentType.Cert));
            root.Add(publicCert);
        }
    }

But adapt this correctly to the project's .NET Framework version and existing architecture.

7. CA-ISSUED CERTIFICATES
============================================================

If:

    Subject != Issuer

and the chain is untrusted:

DO NOT automatically trust the leaf certificate as a root.

Instead determine and log the chain problem.

Examples:

    PartialChain
    UntrustedRoot
    NotTimeValid
    RevocationStatusUnknown
    OfflineRevocation

For a CA-issued certificate with missing root/intermediate:

show an installer warning such as:

    The Laserfiche HTTPS certificate is issued by <issuer>,
    but Windows does not currently trust its certificate chain.

    Install the issuing/root CA certificate in the Local Computer
    certificate store and retry.

If an intermediate certificate is available from the chain and Windows can safely place it into Intermediate Certification Authorities, that may be handled separately, but DO NOT turn a normal leaf certificate into a trusted root.

8. HOSTNAME VALIDATION
============================================================

Do not assume localhost.

The installer must choose a ServerUrl whose host matches the certificate.

Candidate hosts may include:

1. explicit IIS HTTPS binding host
2. certificate SAN DNS names
3. machine FQDN
4. machine hostname
5. localhost
6. configured Laserfiche endpoint

But a candidate may only be selected if:

- it resolves/reaches the local Laserfiche API
- the IIS binding serves the API
- TLS certificate identity matches it

IP addresses should only be selected if the certificate has the corresponding IP SAN.

Do not treat CN/SAN DNS=localhost as valid for 192.168.x.x.

Our test proved why:

machine IP was:

    192.168.102.111

while an old certificate was:

    192.168.102.112

and TCP 443 to 192.168.102.112 timed out.

localhost, however, returned HTTP 200.

Therefore discovery must use the CURRENT environment, never stale IP information.
